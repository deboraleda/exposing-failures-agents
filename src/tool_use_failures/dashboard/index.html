Corrupt Success in Tool-Calling Agents

Problematic Tool Calls Behind Passing Runs

    Agents under test

    Each agent targets one kind of tool-calling failure. A baseline case is a direct request; a conflicting case is built to push the agent into that failure. Every number in this dashboard refers to these nine agents; Eureca Chat has its own tab.

    Deterministic pass rate by case group

    Share of runs that pass the deterministic oracle: the expected tools, the allowed number of calls and the expected arguments. Judges play no part here.

    LLM judge verdict against the deterministic oracle

    Each judged run falls in one of four outcomes. A judge passes a run when its TaskCompletion score is at least 0.7. Corrupt success is a run the judge approves although its tool calls fail the oracle.

    True success judge pass, oracle pass Corrupt success judge pass, oracle fail False failure judge fail, oracle pass True failure judge fail, oracle fail

    How well each judge tracks the oracle

    The deterministic oracle is the ground truth and each judge a classifier of "this run succeeded".

    PrecisionOf the runs a judge approved, the share that also passed the oracle. TS / (TS + CS). Low precision means the judge hands out corrupt successes.
    RecallOf the runs that passed the oracle, the share the judge also approved. TS / (TS + FF). Low recall means the judge rejects runs whose tool calls were right.
    F1Harmonic mean of precision and recall. 2PR / (P + R). It is high only when both are high.

    A corrupt success from each agent

    For each agent, the run approved by the most judges (then with the highest judge score) among the runs that failed the oracle.

    Eureca Chat: an exploratory study

    A beta university assistant developed outside this study, which answers academic questions by querying the university's database and documents through tools. Ten questions (five clear, five ambiguous) were each run ten times with the three executor models, and a deterministic oracle checked the tool calls against the expected and allowed tools. The same two LLM judges of the main study then scored the final responses (TaskCompletion, pass at 0.7), so corrupt success is measured as in the other tabs: a run the judge approves although it fails the oracle.

    Not part of the main results. These runs are kept out of every card, table and count in the other tabs, which refer only to the nine agents of the study. They support the Discussion of the paper.

    How the numbers are made
    • Every run of every case is checked deterministically by its experiment: whether the expected tools were called, how many times and with which arguments. That check is the oracle.
    • Each run's final answer is also scored by the LLM judges with DeepEval's TaskCompletion metric. A score of 0.7 or more is a pass. Judge errors are left out of the matrices and of precision, recall and F1.
    • Runs that crashed before finishing (for example, the provider was overloaded) are left out of every count.
    • Cases whose id starts with am_ or inj_ are conflicting; every other case is baseline. Each agent keeps 4 baseline and 4 conflicting cases: nt_1 of Academic triage and eq_1 and eq_2 of Order support are left out.
    • For each agent and executor model, only the most recent result file is used.
